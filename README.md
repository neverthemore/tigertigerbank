## 🏦 Предметная область

Программа моделирует **управление личными финансами** пользователя. Основные сущности:

| Класс          | Описание                                                                 |
|----------------|--------------------------------------------------------------------------|
| `BankAccount`  | Счёт пользователя: уникальный ID, название, текущий баланс.              |
| `Category`     | Категория операции: тип (INCOME / EXPENSE), название (например, «Зарплата», «Кафе»). |
| `Operation`    | Финансовая операция: тип, сумма, дата, описание, ссылки на счёт и категорию. |

Пользователь может:
- ➕ создавать, редактировать и удалять счета, категории, операции;
- 📊 получать аналитику: разницу доходов/расходов за период, группировку по категориям;
- 💾 экспортировать и импортировать данные в форматах JSON, YAML, CSV;
- 🔄 автоматически пересчитывать баланс при создании/удалении операций.

Все бизнес-правила соблюдены: нельзя создать операцию с отрицательной суммой, нельзя списать больше, чем есть на счету, тип операции должен совпадать с типом категории.

## 🛠 Технологии и подходы

### 🔹 Единый code style
Код оформлен в соответствии с **Java Code Conventions**:
- отступы — 4 пробела;
- фигурные скобки на той же строке;
- осмысленные имена переменных;
- отсутствие магических чисел (всё вынесено в константы или параметры).  
Проект легко читать и поддерживать.

### 🔹 Принципы SOLID
1. **Single Responsibility**  
   - `BankAccount` отвечает только за состояние счёта, `AccountService` — за бизнес-логику, `InMemoryAccountRepository` — за хранение.
2. **Open/Closed**  
   - Интерфейсы репозиториев (`AccountRepository`, `CategoryRepository`) позволяют добавлять новые реализации (например, для работы с БД) без изменения существующего кода.
3. **Liskov Substitution**  
   - Любая реализация репозитория может быть подставлена вместо интерфейса.
4. **Interface Segregation**  
   - Интерфейсы дробные, содержат только необходимые методы.
5. **Dependency Inversion**  
   - Модули верхнего уровня (сервисы) зависят от абстракций, а не от конкретных классов. Это реализовано через DI-контейнер.

### 🔹 Взаимодействие модулей через DI-контейнер
Создан простой **ручной DI-контейнер** (`DIContainer`), который:
- регистрирует зависимости (синглтоны или фабрики);
- разрешает их при создании объектов.
Пример:
```java
container.register(AccountService.class, () -> new AccountService(
    container.resolve(AccountRepository.class)
));
```
Благодаря этому сервисы не знают о конкретных реализациях репозиториев, а тестирование становится простым (можно подменить репозиторий моком).

## 📁 Работа с файлами

Реализован **импорт и экспорт данных** (операций) в трёх форматах:
- **JSON** (Jackson) — `JSONOperationExporter` / `JSONOperationImporter`
- **YAML** (Jackson) — `YAMLOperationExporter` / `YAMLOperationImporter`
- **CSV** (ручной парсинг) — `CSVOperationExporter` / `CSVOperationImporter`

Все классы реализуют общие интерфейсы `DataExporter<T>` и `DataImporter<T>`, что позволяет легко добавить новый формат (например, XML) без изменения существующего кода — **Open/Closed** в действии! 💪

Файлы сохраняются в корень проекта с именами `operations.json`, `operations.yaml`, `operations.csv`.

## 🚧 Проблемы при расширении бизнес-логики

Несмотря на все абстракции, некоторые изменения могут потребовать модификации существующего кода:
- **Добавление новой сущности** (например, «Бюджет» или «Цель») — придётся создавать новые репозитории, сервисы и, возможно, менять существующие сервисы, которые работают с операциями.
- **Изменение логики валидации** (например, введение лимитов по категориям) — потребуется править методы сервисов.
- **Введение транзакционности** — текущая in-memory реализация не поддерживает атомарность, но интерфейсы репозиториев позволят заменить их на транзакционные без изменения бизнес-логики.
- **Добавление нового формата импорта** — легко через новые классы, реализующие `DataImporter`.

Таким образом, абстракции помогают локализовать изменения, но не могут полностью исключить модификаций при кардинальном расширении функционала.

## 💡 Почему абстракции улучшили дизайн

1. **Гибкость хранилища**  
   Интерфейсы репозиториев позволяют легко заменить in-memory реализацию на работу с базой данных или файлами — достаточно создать новый класс и зарегистрировать его в DI-контейнере.

2. **Лёгкость тестирования**  
   Благодаря DI мы можем подставлять моки или специальные тестовые реализации, не затрагивая основную логику.

3. **Расширяемость форматов**  
   Единые интерфейсы для импорта/экспорта позволяют добавлять новые форматы (XML, Excel и т.д.) без изменения кода, работающего с операциями.

4. **Читаемость и поддержка**  
   Каждый класс отвечает за свою задачу, код не перегружен лишними зависимостями, его легко рефакторить.

5. **Соответствие SOLID**  
   Все принципы соблюдены, что делает систему устойчивой к изменениям и понятной для новых разработчиков.
